# 범용 에이전트 지침

> 개인 엔지니어링 정책 · 한국어 · 2026-09-28

## G01 — 범위와 필수 문서

이 정책은 이전 작업에서 기억하는 저장소가 아니라 현재 프로젝트에 적용한다. Rust 작업은 [RUST.md](../../RUST.md), TypeScript 작업은 [TYPESCRIPT.md](TYPESCRIPT.md), TSX 작업은 [TYPESCRIPT.md](TYPESCRIPT.md)와 [TSX.md](TSX.md)를 읽는다. 다른 언어에는 일반 엔지니어링 규칙만 적용하고 맞지 않는 문법 규칙을 강요하지 않는다.

이 문서는 개인 코딩 스타일이다. 모든 커뮤니티나 포매터가 같은 방식을 쓴다는 뜻은 아니다. 영어·인도네시아어·한국어판은 동등한 규칙을 담는다. 한 언어판만 선택하고 번역본을 서로 다른 정책처럼 중복해서 읽지 않는다.

실행 환경의 지침 우선순위, 현재 사용자 요청, 적용되는 저장소 지침, 실제 호환성 제약을 존중한다. 도입할 때 충돌하는 스타일 규칙을 명시적으로 조정한다. 더 엄격한 안전·보안·라이선스·제품 요구사항을 유지한다. 이 템플릿으로 이를 몰래 덮어쓰지 않는다.

## G02 — 유지할 스타일

- 읽기 쉬운 시그니처와 호출은 가로로 유지하고 초기 목표는 120열로 한다. 프로젝트에서 명시적으로 승인한 경우에만 140열을 쓴다. 의미 있는 이름을 줄이거나 모든 인수를 한 줄씩 늘어놓지 않는다.
- 비어 있지 않은 여러 줄 중괄호 본문의 시작과 끝 안쪽에 빈 줄을 하나씩 둔다. 관련 문장은 붙여 두고 서로 다른 논리 단계 사이에만 빈 줄 하나를 둔다. 모든 문장 사이에 빈 줄을 넣지 않는다. 문법 예외는 언어별 지침을 따른다.
- 상수와 static을 포함한 프로젝트 소유 값 식별자는 소문자 `snake_case`로 작성한다. 타입·컴포넌트 이름과 외부 계약의 예외는 언어별 지침을 따른다.
- TypeScript/TSX의 대입 `=`와 import `from`은 작고 연속된 논리 그룹 안에서 정렬한다. 여러 줄 JSX prop 대입도 정렬한다. 파일 전체를 한 열에 맞추지 않는다. Rust 대입 정렬은 필수가 아니다.
- 테스트 본문, mock, fixture, 테스트 설정은 프로덕션 `src/` 밖에 둔다. 기존 커버리지를 유지하되 파일을 옮길 때마다 테스트를 만들지 않는다.
- 파일 수나 줄 수를 줄이거나 추상화를 늘리는 것보다 명확한 소유권, 실제 재사용, 작고 안전한 변경, 측정된 개선을 우선한다.

## G03 — 실제 환경 파악

작업 디렉터리, 브랜치, 스테이징 여부별 변경, 추적되지 않은 작업, 관련 소유 모듈, manifest, lockfile, 도구, 스크립트, 하위 지침을 확인한다. 동작 변경 전 필요한 호출부를 읽는다. 오래된 스크린샷과 계획은 단서이지 현재 소스의 근거가 아니다.

운영체제, 프레임워크, 패키지 관리자, 저장소 이름, 디렉터리 구조, 모델 공급자, 보조 에이전트 수, 저장 공간 기준, 주사율 목표를 가정하지 않는다. 정리를 위해서만 의존성을 설치하거나 버전을 변경하지 않는다.

내부 engineering 이름은 영어로 유지한다. 새 프로젝트 소유 코드 주석은 자연스러운 대화체 **반말** 한국어로 쓴다. `보여줘`, `돌려줘`, `막아`처럼 편한 maintainer 말투를 쓰되 기술적 의미는 정확하게 유지한다. 모든 주석에 slang, 농담, emoji, `ㅋㅋ`를 강제로 넣지 않는다. identifier, API 이름, documentation tag, 관례적인 기술 heading은 정확히 유지한다. 이는 custom 문체 선호이며 언어나 tooling의 표준이 아니다. 기존 사용자 화면 언어, 현지화 key, API 텍스트 계약, 더 엄격한 프로젝트 문서 언어 요구사항은 유지한다. 이 번역 지침은 계속 의도적인 다국어 문서다.

문서 주석은 전문적인 계약으로 작성한다. 먼저 책임을 짧게 설명하고 실제로 관련 있는 동작, input 제한, absence/fallback 규칙, side effect, ownership/resource lifetime, cancellation, 부분 실패, retry 조건, safety invariant를 추가한다. caller가 구현을 읽지 않고도 쓸 수 있도록 public API를 문서화한다. 실제 계약에 맞춰 상세도를 조절하며 모든 item에 모든 heading을 만들거나 signature에 이미 보이는 type을 반복하지 않는다.

해당 언어의 documentation 문법과 지원되는 tag를 사용한다. logic 안의 일반 주석은 바로 알기 어려운 결정이나 invariant를 설명한다. 이름만 반복하는 `begin`/`end` marker는 유용한 계약 설명으로 바꾸고 banner, statement별 설명, 장식용 author/date/version metadata는 피한다. 문서는 owner에 붙여 두고 동작이 바뀌면 함께 수정한다. atomicity, thread safety, 안전한 retry 같은 주장은 구현 근거가 필요하며 예시와 실패 설명은 실제 코드와 일치해야 한다.

## G04 — 멈춰 있지 않되 안전하게 실행

다음 순서를 따른다: **소유 모듈과 필요한 호출부 확인 → 일관된 변경 묶음 편집 → diff 검토 → 범위에 맞는 검증 → 계속 진행**.

이미 이해한 저위험 변경은 같은 소유 범위에서 묶는다. 위험한 동작 변경은 신속하게 검증한다. 전체 검사는 매 줄이 아니라 통합 시점에 실행한다. 최적화나 위험한 동작 변경 전 관련 기준값을 기록한다. 새로운 이유 없이 같은 검색이나 빌드를 반복하지 않는다.

명령과 포매터는 정당한 도구이며 최종 결과물 자체는 아니다. 수동 타이핑이 자동 편집보다 본질적으로 안전한 것은 아니다. 범위, 의미 보존, 검토한 결과로 판단한다. 끝없는 조사와 무작정 하는 저장소 전체 재작성 모두 피한다.

포매팅, 이름 변경·이동, 정확성 수정, 최적화를 검토 가능한 묶음으로 나눈다. 사용자가 다른 방식을 요청하지 않았다면 작업 브랜치를 사용한다. 무관한 수정과 스테이징된 작업을 보호한다. 승인받은 경우에만 commit/push한다. 강제 push, 파괴적인 reset/restore/clean, 자동 merge, release는 하지 않는다.

승인된 모든 소유 범위까지 작업을 이어 간다. 실제 장애물이 생기면 해당 부분을 멈추고 필요한 조건을 정확히 설명하며 독립적으로 가능한 안전한 작업은 계속한다. 계획을 처음부터 다시 쓰거나 바쁘게 보이려고 범위를 추가하지 않는다.

## G05 — 주 담당자와 선택적 하위 에이전트

주 엔지니어가 설계, 프로덕션 변경, 위험한 구현, 통합, 최종 검증을 책임진다. 특정 모델을 요구하지 않는다. 보조 에이전트는 기본적으로 읽기 전용이며 참조 탐색, 의존성 매핑, 중복 분석, 테스트 영향, 측정, diff 검토를 맡는다. 발견 사항에는 정확한 파일·심볼과 근거가 필요하다.

자동으로 위임하지 않는다. 실제로 사용 가능하며 허용된 에이전트와 동시 실행만 사용한다. 재귀적 위임, 추가 채팅 스레드, 사용할 수 없는 기능을 흉내 내기 위한 백그라운드 작업을 만들지 않는다. 각 보조 에이전트에 한정된 범위를 주고 같은 worktree에서 충돌하는 편집이나 무거운 빌드를 실행하지 않는다.

보조 에이전트의 파일 쓰기는 명시적인 범위 제한 승인이 있을 때만 허용한다. 정리 작업은 지정된 실행자 한 명이 수행하며 병렬 삭제 worker를 사용하지 않는다. 에이전트 운영 제한이 기존 애플리케이션 설계에 필요한 정상적인 thread나 worker를 금지하는 것은 아니다.

## G06 — 파일·폴더와 소유권

루트에는 필요한 소스·패키지 루트, 도구, 유지 관리되는 문서, 필수 설정만 둔다. 현재 프레임워크의 진입점과 라우팅 규칙을 따른다. 다른 프로젝트가 사용했다는 이유로 `apps/`, `features/`, `landing/` 또는 workspace를 만들지 않는다.

실제 기능·도메인 기준으로 코드를 묶는다. 공용 시각 요소, 공용 인프라, 기능 전용 코드는 서로 다른 책임을 가진다. 비공개 helper는 소유 모듈 가까이 둔다. 재사용 함수는 반복 동작을 제거하거나 실질적인 경계를 만들 때 추출하고, 호출 하나를 감싸기 위해 만들지 않는다.

임의의 파일 개수로 폴더를 강제하거나 빈 scaffold를 만들지 않는다. 모든 helper를 파일로 쪼개거나 잡다한 `utils` 폴더를 두지 않는다. 예시 tree는 책임 지도이며 실제 목록이나 삭제 체크리스트가 아니다.

이동 전에 `이전 경로 → 새 경로 → 소유 모듈 → 사용처 → 테스트`를 기록한다. 충돌, import, export, 조건부 모듈, textual include, 생성 입력, asset URL, 동적 import, worker, snapshot, mock, route, 빌드 스크립트, CI 필터, 문서 링크를 확인한다. 더 깊은 분리를 검토하기 전에 관련 그룹을 먼저 이동한다.

공개 API, 직렬화, 저장 데이터, UI, 권한 검증, resource 수명, timing을 유지한다. 필요한 호환 shim은 사용처와 제거 계획이 명확해야 한다. 두 활성 구현을 남기지 않는다.

## G07 — 공용 데이터와 최적화

탐색·로딩, 식별 검증, 최신 값 샘플링, 순수 데이터 접근을 분리한다. 함수 재사용이 결과 재사용을 자동으로 의미하지는 않는다. getter나 selector 안에 scan, 네트워크 호출, blocking wait를 숨기지 않는다.

공유 state는 실제 수명 범위 안에서 한 곳이 책임진다. 경쟁하는 store/service를 추가하기 전에 기존 것을 사용한다. 식별 정보와 변하는 값을 구분해서 cache한다. identity/session 교체, 제거, 버전 변경, 관련 입력 변경 시 무효화하고 오래된 작업의 늦은 결과는 거부한다.

근거가 있을 때 일관된 snapshot과 크기가 제한된 buffer를 재사용한다. reader의 불변성과 freshness metadata를 보존한다. 비활성 consumer만 필요한 작업은 중단하되 활성 consumer를 굶기지 않는다. cancellation, resource 해제, queue 한도를 명시한다.

조건이 같은 변경 전후 시나리오를 측정한다. 관련 latency, throughput, allocation, read, queue 깊이, CPU/RAM, 데이터 나이, rendering 비용을 보고한다. 측정하지 않은 값은 미측정으로 남기고 0을 만들어 내지 않는다. 속도 개선을 주장하려고 정확성, 보안, 접근성, freshness, presentation 품질을 낮추지 않는다. 보편적인 frame cap이나 주사율 대신 프로젝트의 실제 서비스·성능 목표를 사용한다.

## G08 — 절제된 테스트

동작을 유지하는 포매팅, naming, 이동에서는 유용한 기존 테스트를 옮기고 수정한 뒤 관련 suite를 실행한다. 실제 버그, 동작 변경, 위험한 lifecycle, 구체적인 미검증 회귀에 가장 작은 집중 테스트를 추가한다. 포매터 작업에는 작은 golden·멱등성 테스트가 필요할 수 있지만 모든 파일의 외관을 검사할 이유는 아니다.

유용한 테스트를 삭제하거나 assertion을 약화하지 않는다. discovery에서 테스트를 숨기거나 이동을 통과시키려고 프로덕션 API를 넓히지 않는다. 테스트 양은 품질 지표가 아니다. unit suite는 소스 소유 구조를 따라 패키지의 `tests/unit/`에 두고 integration suite는 실제 runner가 발견하는 위치에 둔다. 언어가 요구하는 연결 코드와 유용한 실행 가능한 문서 예시는 유지한다.

공용 fixture/mock은 `tests/`에, 기능 전용 fixture는 해당 suite 옆에 둔다. 자동 visual/end-to-end 테스트는 프로젝트 runner 설정을 따른다. 수동 QA 지침과 필수 참조 이미지는 관리 대상이며 임시 쓰레기가 아니다.

## G09 — 안전한 정리

승인된 저장소·출력 범위 안에서 폐기 가능하고 비활성임이 확인된 항목만 삭제한다. 이상한 이름, 오래된 날짜, ignore된 경로, 단순 텍스트 검색 결과가 없다는 사실만으로 불필요하다고 판단하지 않는다. build/test/release/tool 사용처와 동적 참조를 확인한다. 불확실한 항목과 작업과 무관한 dirty/untracked 사용자 파일은 보존한다.

활성 소스, 로컬 설정, 비밀 정보, fixture, 라이선스 asset, release 증거, 의도적으로 보관된 archive를 보호한다. Explorer를 깨끗하게 만들기 위해 dependency 폴더나 활성 빌드 출력을 삭제하지 않는다. 승인 범위 밖으로 symlink를 따라가지 않는다.

검증된 폐기 경로에만 ignore 규칙을 추가한다. ignore는 이미 추적 중인 파일을 해제하지 않으며 편집기에서 숨김을 보장하지도 않는다. 유용한 계획·연구는 관리 문서로 옮기고 링크를 수정한다. 실제로 쓰이지 않는 빈 폴더만 삭제하며 프레임워크 필수 디렉터리는 유지한다.

## G10 — 저장 공간과 resource

무거운 설치·빌드 전에 현재 프로젝트의 저장 공간 정책을 읽는다. 관련 volume의 여유 공간을 측정하고 문서화된 최소값과 작업 여유분을 지킨다. 기준이 없다면 작업에 필요한 용량을 추정하고 중요한 불확실성을 알린다. 임의의 고정 용량 기준을 만들지 않는다.

공간이 부족하면 무거운 작업은 멈추고 안전한 가벼운 작업을 계속한다. 허가된 비활성 폐기 출력만 정리한다. 이 템플릿은 PC 전체 정리, 개인 파일 삭제, 무관한 process 종료, 시스템 설정 변경을 허가하지 않는다. 공간 부족으로 막힌 빌드를 반복해서 시도하지 않는다.

## G11 — 도구와 근거

알고 있는 파일에는 직접 읽기·검색을 사용한다. 소유권이나 참조가 불분명할 때 semantic 도구를 사용한다. API가 불확실하면 사용 가능한 문서 도구와 1차 자료를 활용하고 고정 버전과 플랫폼 의미를 확인한다. 실제로 확인하기 전 도구·명령이 있다고 주장하지 않으며 로그에 credential을 노출하지 않는다.

편집기와 CI에서 승인된 단일 formatting pipeline을 사용한다. custom padding/alignment는 반복 실행해도 유지되고 literal과 의미를 바꾸지 않아야 한다. 대표 소유 모듈을 먼저 시험한다. 포매터와 충돌하면 차이를 설명하고 작은 syntax-aware 해결책에 합의한다. 일괄 skip이나 별개의 거대 포매터 프로젝트를 만들지 않는다.

compiler/type/lint/test gate를 유지한다. 수정 전 관련 diagnostic 전체를 읽는다. 실제 저장소 명령을 올바른 작업 디렉터리, target, feature, lockfile 정책으로 실행한다. 정적 검사는 runtime, visual, integration, performance 검증이 아니다.

## G12 — 완료 조건

승인된 구현, 파일 구조, 스타일, 필요한 정확성 수정, 범위별 검증, 허가된 정리를 마친다. **변경**, **검증**, **미검증**, **차단됨**을 실제 명령·결과·측정과 함께 보고한다. 버그가 없다고 보장하거나 근거 없이 빌드 성공을 주장하지 않는다.

프로젝트별 사실은 작은 로컬 항목에 기록한다. 실제 root, 명령, 지원 platform, 계약, 성능·저장 공간 한도, 사용 가능한 도구, 위임 권한이 해당한다. 이를 범용 기본값으로 복사하지 않는다. 번역 간 section ID와 규칙의 동등성을 유지한다.
